단일 페이지 세로 스크롤 + 모달 조합. 라우팅 없음. 앵커 이동만.

```
[고정 헤더]  로고 "업다운 팬클럽!" · 입덕 카운터 · [활동 규칙] · [내 이름표]
    │
    ├─ 0. 공지 배너            (범쨩 공지 있을 때만 노출)
    ├─ 1. 인기글               #hot
    ├─ 2. 최근 주접            #recent   + [주접 쓰기] FAB
    ├─ 3. 인사해요             #hello
    ├─ 4. 팬미팅               #fanmeeting
    ├─ 5. 사장님 활동 페이지    #links
    └─ [푸터]  비공식 고지 · 신고 안내 · 데이터 삭제 요청 안내

[모달 레이어]
    M1. 닉네임 등록 / 이름표 만들기
    M2. 범쨩 인증 (8자리)
    M3. PIN 설정 (4자리)
    M4. PIN 확인 (수정·삭제용)
    M5. 활동 규칙
    M6. 인사 작성 (질문 4개 폼)
    M7. 주접 작성 / 수정
    M8. 주접 상세 + 댓글

    T. 토스트 (하단 고정, 2.5초)
```

### 스크롤 순서를 이렇게 잡은 이유

- **인기글 → 최근 주접** 순서: 처음 온 사람이 제일 재밌는 걸 먼저 본다. 참여 동기가 여기서 생긴다.
- **인사해요를 피드 아래**: 위에 두면 가입 폼처럼 보여서 튕긴다. "재밌네 → 나도 쓸래 → 어 인사해야 하네" 흐름이 자연스럽다.
- **팬미팅을 인사 뒤**: 하루 1회짜리는 이미 들어온 사람의 리텐션 장치다. 첫 화면에 둘 필요 없다.
- **활동 페이지는 마지막**: 페이지를 다 본 사람을 실제 금샘탕/공식 채널로 내보내는 출구.

```js
function getRole(member) {
```

## 3. 닉네임 & 비밀번호 정책

### 3-1. 닉네임 규칙

| 항목 | 규칙 | 위반 시 인라인 메시지 |
|------|------|----------------------|
| 길이 | 2~12자 (공백 제외 기준) | "두 글자는 넘겨주세요" / "열두 글자가 한계예요. 줄여주실 수 있죠?" |
| 허용 문자 | 한글(완성형) · 영문 · 숫자 · `_` · `-` · 공백 1개까지 | "한글, 영문, 숫자랑 `_` `-` 정도만 받아요" |
| 금지 문자 | 이모지, 특수기호, 제어문자, 전각 공백, 연속 공백, 앞뒤 공백 | "이모지는 닉네임에 안 들어가요. 본문에서 쓰세요" |
| 정규화 | NFC 정규화 → 앞뒤 trim → 연속 공백 1개로 축약 | (자동 처리, 안내 없음) |
| 중복 판정 | **정규화 키**로 비교: `nickKey = NFC(nick).toLowerCase().replace(/\s/g,'')` <br>→ `범 쨩` `범쨩` `BUM` `bum` 은 전부 같은 키 | "그 이름은 벌써 누가 찜했어요. 뒤에 숫자라도 붙여보실래요?" |
| 금지어 | 욕설, 성적 표현, 타인 실명 패턴, `금샘탕공식` `사장님` `운영자` `관리자` `admin` `공지` 등 사칭성 단어 | "그 이름은 오해 살 수 있어서 못 써요. 다른 걸로!" |
| 예약어 | `범쨩` `범짱` `bumjjang` 및 그 변형 → §3-2 분기 | (별도 모달) |

> 금지어 리스트는 클라이언트 상수 배열이다. 우회는 당연히 가능하다. **거르는 게 목적이 아니라 대충 쓴 사람이 멈칫하게 만드는 게 목적.** 뚫고 들어온 건 범쨩이 지운다.

**검증 방식**

```js
// 코드에 하드코딩되는 값 (평문 비번이 아니라 해시)
const ADMIN_HASH = '...64자리 hex...';   // ← 배포 전 범쨩 본인 비번으로 생성해 교체

async function checkAdmin(input) {
  return (await derive('범쨩', input)) === ADMIN_HASH;
}
```

**시도 제한 저장**: `localStorage['gst_v1_admin_fail']` = `{count, lockUntil}`
→ localStorage 지우면 초기화된다. **알고 있고, 그대로 간다.** 8자리 브루트포스를 브라우저에서 손으로 돌릴 사람은 없다는 쪽에 건다.

### 3-3. 4자리 PIN의 용도와 해싱

**용도는 딱 하나**: 내가 쓴 **주접 글·댓글·인사·팬미팅 질문을 수정/삭제할 때 본인 확인**.
로그인 수단이 아니다. 공감에는 안 쓴다. 읽기에는 당연히 안 쓴다.

**평문 저장 절대 금지.** 최소 기준은 SHA-256, 권장은 PBKDF2.

```js
const SALT = 'geumsaemtang-updown-fanclub-v1';   // 코드에 박히는 고정 salt (공개된 값)

// 권장: PBKDF2 (느려서 대량 시도에 불리하게 만듦)
async function derive(nickKey, pin) {
  const enc = new TextEncoder();
  const key = await crypto.subtle.importKey(
    'raw', enc.encode(`${nickKey}::${pin}`), 'PBKDF2', false, ['deriveBits']
  );
  const bits = await crypto.subtle.deriveBits(
    { name: 'PBKDF2', salt: enc.encode(`${SALT}::${nickKey}`), iterations: 150000, hash: 'SHA-256' },
    key, 256
  );
  return [...new Uint8Array(bits)].map(b => b.toString(16).padStart(2, '0')).join('');
}

// 최소안: SHA-256 1회 (PBKDF2가 느려서 못 쓸 때만)
async function digest(nickKey, pin) {
  const buf = await crypto.subtle.digest('SHA-256',
    new TextEncoder().encode(`${nickKey}::${SALT}::${pin}`));
  return [...new Uint8Array(buf)].map(b => b.toString(16).padStart(2, '0')).join('');
}
```

**닉네임을 salt와 입력값 양쪽에 섞는 이유**: 같은 PIN `1234` 를 쓴 사람들의 해시가 전부 달라진다. DB를 통째로 본 사람이 "해시 같은 놈들 = 같은 비번" 을 못 뽑는다.

#### 이게 보안이 아닌 이유 (솔직하게)

| 한계 | 설명 |
|------|------|
| salt가 공개됨 | HTML 소스에 그대로 박혀 있다. 숨길 곳이 없다. |
| 경우의 수 1만 개 | 4자리 숫자는 `0000`~`9999`. PBKDF2 15만회를 걸어도 한 계정 전수조사에 수십 분이면 끝난다. |
| DB가 열려 있음 | 공유 DB는 페이지를 여는 누구나 읽고 쓸 수 있다. `pinHash` 도 보인다. |
| 검증 주체가 클라이언트 | "맞으면 삭제 실행" 이 브라우저 안에서 일어난다. 분기를 건너뛰고 `delete` 를 직접 부르면 그만이다. |
| 비번 재설정 불가 | 서버도 이메일도 없다. 잊으면 복구 못 한다. |

**그래서 이렇게 대응한다**
- PIN 입력창에 **"진짜 비밀번호 재사용 금지"** 를 문구로 박는다 → "다른 데서 쓰는 비번은 쓰지 마세요. 여긴 그렇게 튼튼한 곳이 아니에요."
- 개인정보·연락처·실명은 **입력받지 않는다.** 털릴 게 없으면 털려도 된다.
- 최후 방어선은 암호가 아니라 **범쨩의 삭제 권한 + 신고 버튼**.

### 3-4. 로컬 세션 유지

`localStorage` 사용. 키 prefix `gst_v1_` (스키마 변경 시 `v2_` 로 올려 통째로 무효화).

| 키 | 값 | 용도 |
|----|----|------|
| `gst_v1_nick` | `"온탕러버"` | 화면 표시용 원본 닉네임 |
| `gst_v1_key` | `"온탕러버"` | 정규화 키. 모든 문서 id/조회의 기준 |
| `gst_v1_auth` | PIN 해시 | 수정·삭제 시 재입력 없이 통과 (§3-3 주의문구 동반) |
| `gst_v1_role` | `guest\|member\|full\|admin` | 렌더 분기 캐시 (진실은 항상 DB의 members 문서) |
| `gst_v1_joined` | `1789...` (ms) | 입덕 카운터 오프라인 계산용 |
| `gst_v1_likes` | `["post_a","post_b"]` | 공감 버튼 즉시 렌더용 캐시 |
| `gst_v1_device` | `"d_9f2a..."` (랜덤 UUID) | 닉네임 선점 경쟁 판별 (§11) |
| `gst_v1_admin_fail` | `{count, lockUntil}` | 범쨩 시도 제한 |
| `gst_v1_feed_cache` | 최근 피드 스냅샷 | DB 장애 시 읽기 폴백 |

**한계와 대응**

| 상황 | 결과 | 대응 |
|------|------|------|
| 다른 기기/브라우저 접속 | 익명 구경꾼으로 리셋 | 헤더 `[이름표 만들기]` → 기존 닉네임 입력 시 **복구 플로우** 진입 (§5-1) |
| 시크릿 모드 | 탭 닫으면 소실 | 등록 모달 하단 고지: "시크릿 창이면 창 닫을 때 이름표도 같이 사라져요" |
| 브라우저 데이터 삭제 | 세션 소실 | 복구 플로우 (PIN 있는 사람만 가능) |
| PIN 미설정 멤버가 기기 변경 | **복구 불가** — 그 닉네임은 영영 못 쓴다 | 등록 시 PIN을 함께 받되 스킵 허용, 스킵하면 안내: "비번 없이 가시면 다른 기기에선 이 이름 못 찾아요" |
| localStorage 차단 환경 | 전부 guest | 모든 접근을 `try/catch` 로 감싸고 실패 시 메모리 폴백 (탭 유지 동안만) |

## 4. 데이터 모델

### 4-0. 공통 규약

- 컬렉션은 **7개 + 부록 2개**: `members` `posts` `comments` `likes` `greetings` `questions` `notices` / `reports` `meta`
- 모든 시각은 **epoch milliseconds (number)** 로 저장. 표시할 때만 KST 변환.
- 날짜 문자열이 필요한 곳은 **KST 기준 `YYYY-MM-DD`** 고정.
  ```js
  const kstDay = (ms = Date.now()) =>
    new Date(ms + 9 * 3600000).toISOString().slice(0, 10);   // '2026-09-18'
  ```
- 문서 id에 들어가는 닉네임은 **항상 `nickKey`** (정규화 소문자·공백제거). 한글이 id에 들어가는 걸 피하고 싶으면 `encodeURIComponent` 로 감싼다.
- 랜덤 조각 생성:
  ```js
  const rid = (n = 6) => Math.random().toString(36).slice(2, 2 + n);
  ```
- `query` 는 **단순 동등 비교만** 가정한다. 정렬·범위·집계는 전부 클라이언트에서 처리한다.
- 모든 문서에 `schema: 1` 을 넣어 나중에 마이그레이션 여지를 남긴다.

### 4-1. `members` — 회원

**id 규칙**: `m_{nickKey}` (예: `m_온탕러버`, `m_bumjjang`)
→ 닉네임 중복 방지를 **문서 id 자체로 처리**한다. `get` 해서 있으면 중복.

```json
{
  "schema": 1,
  "nick": "온탕러버",
  "nickKey": "온탕러버",
  "joinedAt": 1789123456789,
  "joinedDay": "2026-09-18",
  "pinHash": "3f9a1c...e2",
  "greetedAt": 1789209856789,
  "isAdmin": false,
  "lastQuestionDay": "2026-09-18",
  "postCount": 3,
  "deviceHint": "d_9f2a41",
  "updatedAt": 1789209856789
}
```

| 필드 | 타입 | 필수 | 설명 |
|------|------|------|------|
| `nick` | string | O | 화면에 뿌리는 원본 닉네임 (2~12자) |
| `nickKey` | string | O | 정규화 키. id와 동일 |
| `joinedAt` | number | O | 가입 시각(ms). 입덕 카운터 기준 |
| `joinedDay` | string | O | 가입일 KST `YYYY-MM-DD`. 일수 계산 정확도용 (§5-1) |
| `pinHash` | string \| null | X | 4자리 PIN 해시. `null` = 아직 멤버(공감만 가능) |
| `greetedAt` | number \| null | X | 인사 완료 시각. `null`이면 멤버, 값 있으면 **정회원** |
| `isAdmin` | boolean | O | 범쨩 여부 |
| `lastQuestionDay` | string \| null | X | 마지막 팬미팅 질문일 (KST). 하루 1회 1차 검증 |
| `postCount` | number | O | 작성한 주접 수 (프로필 표시 + 도배 감지용, 캐시값) |
| `deviceHint` | string | O | 등록한 기기의 랜덤 id 앞자리. 선점 경쟁 판별용 |
| `updatedAt` | number | O | 마지막 변경 시각 |

### 4-2. `posts` — 주접 글

**id 규칙**: `p_{createdAt}_{rid6}` (예: `p_1789123456789_k3n8qa`)
→ 시각이 앞에 오니 id 사전순 정렬 = 시간순 정렬. `list` 결과를 그대로 뒤집으면 최신순이 된다.

```json
{
  "schema": 1,
  "id": "p_1789123456789_k3n8qa",
  "nick": "온탕러버",
  "nickKey": "온탕러버",
  "body": "오늘 사장님이 수건 두 장 주셨다. 두 장. 이게 무슨 의미인지 아는 사람?",
  "createdAt": 1789123456789,
  "editedAt": null,
  "likeCount": 12,
  "commentCount": 4,
  "pinned": false,
  "hidden": false,
  "hiddenReason": null,
  "reportCount": 0
}
```

| 필드 | 타입 | 설명 |
|------|------|------|
| `id` | string | 문서 id 사본 (목록 렌더 시 편의) |
| `nick` / `nickKey` | string | 작성자. `nickKey` 로 본인 판정 |
| `body` | string | 본문. **1~500자**, 줄바꿈 허용, 연속 공백 3개 이상 축약 |
| `createdAt` | number | 작성 시각 |
| `editedAt` | number \| null | 수정 시각. 값 있으면 카드에 `(수정됨)` 표기 |
| `likeCount` / `commentCount` | number | **캐시값** (진실은 `likes`/`comments` 컬렉션). §11-1 |
| `pinned` | boolean | 범쨩 고정. 최근 주접 최상단 + `📌` 뱃지 |
| `hidden` | boolean | 범쨩 숨김. 본문 대신 "온도 조절 중인 글이에요" 표시, 작성자·범쨩만 원문 열람 |
| `hiddenReason` | string \| null | 숨김 사유 (범쨩 메모, 작성자에게도 노출) |
| `reportCount` | number | 누적 신고 수. 3 이상이면 범쨩 패널 상단으로 |

> `pinHash` 는 posts에 **넣지 않는다.** 검증은 `members/m_{nickKey}.pinHash` 를 조회해서 한다. 해시 복사본을 여기저기 흩뿌릴 이유가 없다.

### 4-3. `comments` — 댓글

**id 규칙**: `c_{postId}_{createdAt}_{rid4}`
(예: `c_p_1789123456789_k3n8qa_1789123999999_a7x2`)
→ id에 postId가 들어가 있어서 `query({postId})` 가 안 먹는 환경에서도 `list` 후 prefix 필터로 건질 수 있다. 이중 안전장치.

```json
{
  "schema": 1,
  "id": "c_p_1789123456789_k3n8qa_1789123999999_a7x2",
  "postId": "p_1789123456789_k3n8qa",
  "nick": "냉탕파",
  "nickKey": "냉탕파",
  "body": "두 장은 확정입니다. 저는 한 장 받았어요.",
  "createdAt": 1789123999999,
  "hidden": false,
  "reportCount": 0
}
```

| 필드 | 타입 | 설명 |
|------|------|------|
| `postId` | string | 부모 글 id. 조회 기준 |
| `body` | string | **1~200자** |
| `hidden` | boolean | 범쨩 숨김 시 "범쨩이 치운 댓글이에요" |
| 나머지 | — | posts와 동일 규약 |

> 요구사항상 "댓글은 닉네임 + 4자리 비번 필수". 여기서도 `pinHash` 사본은 저장하지 않고 `members` 를 참조한다. 댓글을 쓰는 시점에 `pinHash == null` 이면 PIN 설정 모달(M3)이 먼저 뜬다.

### 4-4. `likes` — 공감

**id 규칙**: `like_{postId}_{nickKey}`
(예: `like_p_1789123456789_k3n8qa_온탕러버`)
→ **복합키를 문서 id로 만들어서 중복을 구조적으로 차단한다.** 같은 사람이 열 번 눌러도 문서는 하나. `set` 이 덮어쓰기여도 개수가 늘지 않는다. 취소는 `delete`.

```json
{
  "schema": 1,
  "postId": "p_1789123456789_k3n8qa",
  "nickKey": "온탕러버",
  "createdAt": 1789124111111
}
```

| 필드 | 타입 | 설명 |
|------|------|------|
| `postId` | string | 대상 글 |
| `nickKey` | string | 누른 사람 |
| `createdAt` | number | 누른 시각 |

**정확한 공감 수 = `query('likes', { postId })` 의 길이.** `posts.likeCount` 는 화면용 캐시다.

### 4-5. `greetings` — 인사해요

**id 규칙**: `g_{nickKey}` → **1인 1개.** 두 번 쓰면 덮어쓰기(수정)가 된다.

```json
{
  "schema": 1,
  "nick": "온탕러버",
  "nickKey": "온탕러버",
  "answers": {
    "q1": "수건 건네주시는 손이 따뜻해서요. 그날로 끝났습니다.",
    "q2": "탕 온도 물어보면 1도 단위로 알려주시는 그 프로 정신..",
    "q3": "매일 출석해서 주접 한 줄씩. 100일 채우는 게 목표예요",
    "q4": "열탕 3분 냉탕 1분 무한반복파. 건식은 90도부터 인정"
  },
  "createdAt": 1789209856789,
  "editedAt": null,
  "hidden": false
}
```

| 필드 | 타입 | 설명 |
|------|------|------|
| `answers.q1` | string | 입덕 계기 — **필수**, 5~200자 |
| `answers.q2` | string | 최애 포인트 — **필수**, 5~200자 |
| `answers.q3` | string | 활동 포부 — 선택, 0~200자 |
| `answers.q4` | string | 사우나 취향 — 선택, 0~200자 |
| `createdAt` | number | 이 값이 `members.greetedAt` 으로 복사된다 |

### 4-6. `questions` — 팬미팅 질문

**id 규칙**: `q_{kstDay}_{nickKey}` (예: `q_2026-09-18_온탕러버`)
→ **하루 1회 제한을 문서 id 자체로 강제한다.** 같은 날 두 번 써도 문서는 하나, 두 번째가 첫 번째를 덮어쓸 뿐 총량이 늘지 않는다. UI 검증을 뚫려도 데이터는 안 망가진다.

```json
{
  "schema": 1,
  "id": "q_2026-09-18_온탕러버",
  "nick": "온탕러버",
  "nickKey": "온탕러버",
  "day": "2026-09-18",
  "body": "사장님, 탕 온도는 매일 어떻게 맞추세요? 감으로 하시는 건가요?",
  "createdAt": 1789124222222,
  "answer": null,
  "answeredAt": null,
  "answeredBy": null,
  "hidden": false
}
```

| 필드 | 타입 | 설명 |
|------|------|------|
| `day` | string | KST 작성일. 제한 검증 + 그룹 헤더 |
| `body` | string | **5~200자**, 물음표 없어도 통과 |
| `answer` | string \| null | 사장님 답변. 사장님이 직접 쓰시거나, 다른 데 남기신 답을 범쨩이 옮겨 적는다. `null` = 대기중 |
| `answeredAt` | number \| null | 답변 등록 시각 |
| `answeredBy` | string | 답변 입력한 어드민 nickKey (기록용) |

### 4-7. `notices` — 공지 (범쨩 전용)

**id 규칙**: `notice_active` **단 하나만 사용.** 공지는 동시에 하나. 과거 공지는 안 남긴다.

```json
{
  "schema": 1,
  "active": true,
  "body": "이번 주 화요일 금샘탕 정기휴무입니다. 헛걸음 마세요!",
  "updatedAt": 1789124333333,
  "updatedBy": "bumjjang"
}
```

### 4-8. (부록) `reports` — 신고

**id 규칙**: `r_{targetId}_{nickKey}` → 같은 사람이 같은 글을 여러 번 신고해도 1건.

```json
{
  "schema": 1,
  "targetType": "post",
  "targetId": "p_1789123456789_k3n8qa",
  "nickKey": "냉탕파",
  "reason": "욕설",
  "createdAt": 1789124444444
}
```

`targetType`: `post` \| `comment` \| `greeting` \| `question`
`reason`: `욕설` \| `개인정보` \| `홍보` \| `도배` \| `기타` (고정 5택)

### 4-9. (부록) `meta` — 운영 메타

**id 규칙**: `meta_site`

```json
{
  "schema": 1,
  "openedAt": 1789000000000,
  "memberCount": 47,
  "postCount": 213,
  "lastReconcileAt": 1789124555555
}
```

카운터 캐시. 틀려도 화면 숫자만 어긋나는 값이라 정합성 요구가 낮다. 범쨩 패널에서 수동 재계산 가능.

### 4-10. 컬렉션 요약

| 컬렉션 | id 규칙 | 1인당 문서 수 | 중복 방지 방식 |
|--------|---------|---------------|----------------|
| `members` | `m_{nickKey}` | 1 | id 유일성 |
| `posts` | `p_{createdAt}_{rid6}` | 무제한 (쿨다운 있음) | — |
| `comments` | `c_{postId}_{createdAt}_{rid4}` | 무제한 | — |
| `likes` | `like_{postId}_{nickKey}` | 글당 1 | **복합키 id** |
| `greetings` | `g_{nickKey}` | 1 | id 유일성 |
| `questions` | `q_{kstDay}_{nickKey}` | **하루 1** | **날짜+닉 복합키 id** |
| `notices` | `notice_active` | 전역 1 | 고정 id |
| `reports` | `r_{targetId}_{nickKey}` | 대상당 1 | 복합키 id |
| `meta` | `meta_site` | 전역 1 | 고정 id |

## 5. 기능별 상세 플로우

### 5-1. 닉네임 등록 / 입덕일 계산

**트리거**: 헤더 `[이름표 만들기]` 클릭, 또는 guest가 공감·댓글·주접·질문 시도

**검증 순서**
1. 클라이언트 형식 검증 (§3-1: 길이, 문자, 금지어)
2. 예약어 검사 → `범쨩` 계열이면 M2 분기 (§3-2)
3. `get('members', 'm_' + nickKey)` — 있으면 **복구 플로우**로 전환
4. 없으면 `set` 으로 신규 생성 → **read-after-write 재확인**

```js
const key = normalize(nick);
const id  = 'm_' + key;
const existing = await get('members', id);

if (existing) {
  // 복구 플로우
  if (!existing.pinHash) {
    return toast('그 이름은 벌써 누가 찜했어요. 뒤에 숫자라도 붙여보실래요?');
  }
  openPinModal(async (pin) => {
    if (await derive(key, pin) === existing.pinHash) {
      saveSession(existing);              // 다른 기기에서 이어 하기 성공
      toast(`${existing.nick}님, 다시 오셨네요! ${days(existing)}일째입니다.`);
    } else {
      toast('비번이 안 맞아요. 본인 맞으면 천천히 다시..');
    }
  });
  return;
}

const now = Date.now();
const doc = {
  schema: 1, nick, nickKey: key,
  joinedAt: now, joinedDay: kstDay(now),
  pinHash: pin ? await derive(key, pin) : null,
  greetedAt: null, isAdmin: false,
  lastQuestionDay: null, postCount: 0,
  deviceHint: deviceId(), updatedAt: now
};
await set('members', id, doc);

const check = await get('members', id);          // 동시 선점 판별
if (check.deviceHint !== doc.deviceHint) {
  return toast('아슬아슬하게 누가 먼저 그 이름을 가져갔어요. 다른 이름으로 한 번만 더!');
}
saveSession(doc);
```

**입덕일수 계산**

```js
// 기본 공식 (가입 당일 = 1일째)
const days = (m) => Math.floor((Date.now() - m.joinedAt) / 86400000) + 1;

// 권장 보정: KST 달력 날짜 기준 (자정에 딱 넘어가게)
const daysKst = (m) => {
  const a = Date.parse(m.joinedDay + 'T00:00:00+09:00');
  const b = Date.parse(kstDay() + 'T00:00:00+09:00');
  return Math.round((b - a) / 86400000) + 1;
};
```

> 기본 공식은 "가입한 지 24시간" 기준이라 밤 11시에 가입하면 다음 날 밤 11시에야 2일째가 된다.
> `joinedDay` 를 같이 저장해두면 **KST 자정에 카운터가 올라간다.** 체감상 이쪽이 맞다. 둘 다 저장해두고 표시는 `daysKst` 를 쓴다.

**헤더 표기**

| 상태 | 표기 |
|------|------|
| guest | `입덕 전 구경 중..` |
| member / full | `07일째 입덕 ing..` (2자리 zero-pad, 100일부터 3자리) |
| admin | `132일째 관리 ing..` |
| 1일째 | `01일째 입덕 ing..` (가입 당일) |
| 100일, 200일… | `100일째 입덕 ing..` + 뒤에 `🎉` 대신 텍스트 뱃지 `백일` |

**성공 시 UI 변화**: 헤더 버튼 → 닉네임 드롭다운, 카운터 시작, 공감 버튼 전체 활성, 토스트 `"입덕을 환영합니다. 오늘부터 01일째!"`, 인사해요 섹션으로 부드럽게 스크롤 + 카드 한 번 반짝.

### 5-4. 공감 토글

**트리거**: 카드 하단 공감 버튼

**낙관적 UI 업데이트**
```js
async function toggleLike(post) {
  if (role === 'guest') return promptNickname('like');

  const id = `like_${post.id}_${key}`;
  const liked = likeCache.has(post.id);

  // 1) 화면 먼저 바꾼다 (클릭 즉시)
  likeCache[liked ? 'delete' : 'add'](post.id);
  post.likeCount += liked ? -1 : 1;
  renderLikeButton(post);
  saveLikeCache();

  try {
    // 2) DB는 뒤따라간다
    if (liked) await del('likes', id);
    else       await set('likes', id, { schema:1, postId: post.id, nickKey: key, createdAt: Date.now() });

    // 3) 진짜 개수로 보정 (캐시 갱신)
    const real = (await query('likes', { postId: post.id })).length;
    if (real !== post.likeCount) { post.likeCount = real; renderLikeButton(post); }
    await update('posts', post.id, { likeCount: real });
  } catch (e) {
    // 4) 실패하면 화면 되돌린다
    likeCache[liked ? 'add' : 'delete'](post.id);
    post.likeCount += liked ? 1 : -1;
    renderLikeButton(post);
    toast('공감이 안 눌렸어요. 물이 좀 차네.. 다시 눌러보실래요?');
  }
}
```

**1인 1회 보장**: 문서 id가 `like_{postId}_{nickKey}` 라서 **연타해도 문서는 하나**. 카운트는 `likes` 개수를 세서 맞춘다.
**성공 시 UI**: 하트/온도계 아이콘 채워짐 + 숫자 +1 + 아주 짧은 스케일 애니메이션. 취소 시 역방향.

### 5-6. 팬미팅 질문 (아이디당 하루 1회)

**트리거**: 팬미팅 섹션 입력칸

**검증 (3중)**
```js
const today = kstDay();

// 1차: 로컬 캐시 — 제일 빠름
if (localStorage.getItem('gst_v1_qday') === today) return blocked();

// 2차: members.lastQuestionDay — 기기 바꿔도 걸림
const me = await get('members', 'm_' + key);
if (me.lastQuestionDay === today) return blocked();

// 3차: 문서 id — 최후 방어. 검증을 뚫려도 덮어쓰기만 될 뿐 2개가 안 생김
const qid = `q_${today}_${key}`;
if (await get('questions', qid)) return blocked();
```

**KST 자정 리셋**
- 기준은 **항상 KST**. `kstDay()` 는 UTC+9 를 더한 뒤 `YYYY-MM-DD` 를 자른다. 브라우저 시간대가 어디든 같은 날짜가 나온다.
- 남은 시간 표시:
  ```js
  const msToKstMidnight = () => {
    const now = Date.now();
    const kstNow = now + 9 * 3600000;
    return 86400000 - (kstNow % 86400000);
  };
  ```
- 섹션이 열려 있는 동안 1초마다 카운트다운을 갱신하고, **0이 되면 입력칸을 자동으로 다시 연다** (새로고침 없이).

**쓰기**
```js
await set('questions', qid, { schema:1, id: qid, nick, nickKey: key, day: today,
  body, createdAt: Date.now(), answer: null, answeredAt: null, answeredBy: null, hidden: false });
await update('members', 'm_' + key, { lastQuestionDay: today });
localStorage.setItem('gst_v1_qday', today);
```

**성공 시 UI**: 입력칸이 대기 카드로 바뀜 → `"전달 완료. 사장님 답변 기다리는 중.."` + 자정까지 카운트다운 → 질문 목록 최상단에 내 질문 삽입(`내 질문` 뱃지).

**한계**: 클라이언트 `Date.now()` 를 믿는다. 기기 시계를 돌리면 하루 여러 번 가능하다. 대신 **닉네임 하나당** 이라 티가 나고, 범쨩이 지우면 된다. 시계 조작해서 사장님께 질문 두 번 하는 사람은… 그냥 열정이 넘치는 걸로 치자.

### 5-7. 인기글 랭킹 산정

**공식**

```js
const HALF_LIFE_H = 84;                          // 반감기 3.5일

function hotScore(post, now = Date.now()) {
  if (post.hidden) return -1;                    // 숨긴 글은 제외
  const base  = post.likeCount * 3 + post.commentCount * 2;
  const ageH  = (now - post.createdAt) / 3600000;
  const decay = Math.pow(0.5, ageH / HALF_LIFE_H);
  return base * decay;
}
```

| 요소 | 값 | 이유 |
|------|----|----|
| 공감 가중치 | `× 3` | 한 번 누르면 끝. 참여 비용이 낮으니 단가도 낮게 |
| 댓글 가중치 | `× 2` | 개수는 적지만 글 하나에 여러 개 달릴 수 있어 총합이 커진다. 단가를 낮춰 균형 |
| 시간 감쇠 | `0.5^(경과시간/84h)` | 3.5일에 절반, **7일에 1/4**, 14일에 1/16. 새 글이 못 뚫고 올라오는 고인물 방지 |

**노출 조건**
1. `createdAt` 이 **최근 14일 이내**인 글만 후보 (오래된 건 계산에서 아예 뺀다)
2. `hidden === false`
3. `hotScore >= 3.0` (공감 1개 = 3점이니 **최소 공감 1개** 는 있어야 인기글)
4. 정렬 후 **상위 5개**
5. 후보가 0개면 **인기글 섹션 전체를 DOM에서 숨긴다** (빈 섹션이 제일 초라하다)

**고정글(`pinned`) 처리**: 점수 계산에서 빼고 **최근 주접 최상단 별도 슬롯**에 둔다. 인기글과 섞으면 랭킹이 거짓말이 된다.

**계산 시점**: 페이지 로드 1회 + 공감/댓글 발생 시 해당 글만 재계산 후 재정렬. 전부 클라이언트 메모리 연산이라 200개까지는 체감 0ms.

- 관리 버튼은 `role === 'admin'` 일 때만 **DOM에 생성**한다. 숨기기(`display:none`)가 아니라 안 만든다.
- 파괴적 동작(삭제·밴)은 전부 M11 확인 다이얼로그를 거친다. 범쨩도 손이 미끄러진다.
- 되돌릴 수 없는 삭제 전에 `console.log` 로 문서 스냅샷을 찍어둔다. 최소한의 복구 실마리.

## 9. 사장님 활동 페이지 링크 구조

> **URL은 전부 플레이스홀더다. 임의로 지어내지 않았다.**
> 아래 HTML의 `href="#"` 와 `<!-- TODO -->` 주석 자리에 실제 주소를 채워 넣으면 된다.
> 주소를 못 채운 카드는 **렌더에서 제외**한다 (`href === '#'` 이면 DOM에 안 만듦). 죽은 링크가 제일 없어 보인다.

### 카드 데이터 구조

주소는 사용자가 제공한 실제 값이다. 인스타그램 `stkn`, 유튜브 `si` 같은
공유 토큰은 개인 식별자라 떼고 넣었다. 범쨩이 페이지에서 덮어쓸 수 있고,
덮어쓴 값이 이 기본값보다 우선한다.

```js
const LINKS=[
  {key:'marpple',  platform:'마플샵 스토어',      icon:'shop', url:'https://marpple.shop/kr/geumsaemtang',
   desc:'금샘탕 키링이랑 입장료 할인되는 티셔츠 구경하기'},
  {key:'instagram',platform:'인스타그램',          icon:'ig',   url:'https://www.instagram.com/geumsaemtang',
   desc:'휴무랑 이벤트 소식은 여기가 제일 빨라요'},
  {key:'blog',     platform:'블로그',              icon:'blog', url:'https://m.blog.naver.com/miontang',
   desc:'사장님이 직접 쓰는 긴 이야기. 후기랑 공지는 여기 쌓여요'},
  {key:'youtube',  platform:'유튜브',              icon:'yt',   url:'https://youtube.com/@geumsaemtang',
   desc:'움직이는 금샘탕을 볼 수 있는 유일한 곳'},
  {key:'book',     platform:'집앞목욕탕 금샘탕편', icon:'book', url:'https://m.yes24.com/goods/detail/128861165',
   desc:'금샘탕이 책에 실렸어요. 한 권 통째로 목욕탕 이야기'},
];
```

### 카드 구성 요소

| 요소 | 내용 | 비고 |
|------|------|------|
| 아이콘 | 인라인 SVG 24×24 | 외부 아이콘 라이브러리 안 씀 (단일 파일 원칙) |
| 플랫폼명 | 굵게, 16px | |
| 한 줄 설명 | 회색, 13px | 위 `desc` 그대로 |
| 화살표 | 우측 `↗` | 새 탭 열림 표시 |
| 링크 속성 | `target="_blank" rel="noopener noreferrer"` | 필수 |

**섹션 제목**: `사장님 활동 페이지`
**섹션 서브 카피**: `금샘탕이랑 사우나범 소식은 여기서 챙기세요. 주접만 떨고 가면 섭섭하잖아요.`
**링크 0개일 때 (전부 `#`)**: 섹션 통째로 숨김.
**푸터 고지 (필수)**: `이 페이지는 팬이 만든 비공식 공간이에요. 금샘탕 공식 채널이 아닙니다.`

| 인사 삭제 (범쨩) | `인사를 지우면 이분 정회원 자격도 같이 풀려요.` | `[알겠습니다]` / `[취소]` |
| 이름표 떼기 | `이 기기에서 이름표만 뗍니다. 쓰신 글은 그대로 남아요.` | `[뗄래요]` / `[취소]` |
| 밴 (범쨩) | `이분 글이랑 댓글이 전부 숨겨집니다. 되돌릴 수 있지만 번거로워요.` | `[냉탕으로]` / `[취소]` |

## 11. 엣지 케이스 & 리스크

### 11-1. 동시성 — 공감 카운트 경쟁

| 문제 | 상세 |
|------|------|
| 증상 | A와 B가 같은 글에 동시에 공감 → 둘 다 `likeCount: 5` 를 읽고 `6` 을 쓴다 → 실제 7이어야 하는데 6 |
| 근본 원인 | 공유 DB에 원자적 증가(`increment`)나 트랜잭션이 없다. `read → +1 → write` 사이가 비어 있다 |

**대응**
1. **진실은 `likes` 컬렉션.** `posts.likeCount` 는 렌더용 캐시라고 못 박는다. 틀려도 데이터가 망가진 게 아니다.
2. 공감 직후 `query('likes',{postId})` 로 **개수를 세서** `likeCount` 를 덮어쓴다. 자기 수정형 구조라 다음 클릭에 저절로 맞는다.
3. 글 상세(M8)를 열 때마다 해당 글의 `likeCount`/`commentCount` 를 재계산한다.
4. 카운트를 `update` 로 쓴다 (`set` 은 문서 전체를 날려서 다른 사람의 `pinned` 변경 같은 걸 되돌릴 수 있다).
5. 범쨩 패널 `청소하기` 로 전건 일괄 재계산.

> 그래도 몇 초간 숫자가 1 어긋날 수 있다. **팬클럽 공감 수가 1 틀린 건 사고가 아니다.** 여기에 락을 거는 게 더 큰 손해.

### 11-2. 어뷰징

| 유형 | 가능 여부 | 대응 |
|------|-----------|------|
| 닉네임 여러 개 만들어 자기 글 공감 몰기 | 막을 수 없음 | 랭킹 시간 감쇠(§5-7)로 효과를 짧게, 범쨩이 부자연스러운 글 숨김 |
| 도배 | 부분 차단 | 30초 쿨다운(글) / 10초(댓글) + `postCount` 급증 시 범쨩 패널 `주의` 리스트 |
| 기기 시계 조작으로 팬미팅 하루 여러 번 | 가능 | 닉네임 단위라 티가 남 → 범쨩 삭제. 굳이 서버 시간 API를 붙이진 않는다 |
| 남의 글 무단 삭제 (콘솔에서 `delete` 직접 호출) | 가능 | **막을 방법이 없다.** 대응은 사후 대응뿐 — 범쨩이 복구 못 하는 대신, 파괴적 동작 전 스냅샷 로깅 |
| 금지어 우회 | 쉬움 | 필터는 1차 브레이크일 뿐. 진짜 방어선은 신고 + 범쨩 |
| 범쨩 사칭 | 8자리 인증으로 차단 | 닉네임 `범쨩` 계열 전체를 예약어로 잡아 우회 진입 차단. 유사 닉(`범쨩2`)은 금지어 리스트에 추가 |
| 스팸 링크 | 가능 | 본문에 `http` 포함 시 링크로 렌더하지 않고 **일반 텍스트로만** 표시 (클릭 유도 차단) |
| XSS | 차단 | 모든 사용자 입력은 `textContent` 로만 삽입. `innerHTML` 사용 금지 |

### 11-3. 기기 변경 · 세션 소실

| 상황 | 결과 | 대응 |
|------|------|------|
| PIN 있는 사람 | 복구 가능 | 닉네임 재입력 → PIN 확인 → 세션 복원 (§5-1) |
| PIN 없는 멤버 | **복구 불가** | 등록 시점에 경고 노출. PIN 설정을 강하게 권장하되 강제하진 않음 (공감만 할 사람에게 비번을 요구하면 이탈한다) |
| PIN 분실 | 복구 불가 | 안내: `비번은 복구가 안 돼요.. 지우고 싶은 글이면 신고 눌러주세요, 범쨩이 처리해드립니다.` |
| 입덕 일수 | **안전** | `joinedAt` 은 DB에 있어서 기기 바꿔도 이어진다. 복구만 되면 일수도 그대로 |

### 11-4. DB 미지원 / 장애 폴백

```js
let DB_OK = true;
try { await get('meta', 'meta_site'); } catch { DB_OK = false; }
```

| 모드 | 조건 | 동작 |
|------|------|------|
| 정상 | DB 응답 OK | 전체 기능 |
| **읽기 전용** | DB 읽기만 되고 쓰기 실패 | 모든 입력·버튼 비활성 + 상단 배너 `지금은 구경만 가능해요. 탕물 갈고 있나 봅니다.` |
| **캐시 모드** | DB 읽기도 실패 | `gst_v1_feed_cache` 의 마지막 스냅샷 렌더 + 배너 `마지막으로 봤던 화면이에요. 최신이 아닐 수 있어요.` |
| **정적 모드** | 공유 DB 자체가 없는 환경 | 인터랙션 UI 전부 미생성, 활동 규칙·사장님 링크만 노출 |

- 매 로드 시 피드 상위 20개를 `gst_v1_feed_cache` 에 저장한다 (5KB 내외).
- 모든 DB 호출은 `try/catch` + **2초 타임아웃** + 1회 재시도. 그 이상 매달리지 않는다.

### 11-5. 그 외

| 리스크 | 대응 |
|--------|------|
| 데이터가 커져서 `list` 가 느려짐 | 초기 20개만 렌더 + `[더 보기]` 페이지네이션. 300건 넘어가면 90일 이전 글을 범쨩이 정리 |
| 한글 닉네임이 문서 id에 들어감 | 대부분 문제없지만, id 제약이 걸리면 `encodeURIComponent(nickKey)` 로 감싸고 `members` 에 원본 보관 |
| `nickKey` 충돌로 다른 사람이 같은 취급 | `범 쨩`↔`범쨩` 같은 케이스를 **의도적으로** 같은 키로 묶어 사칭을 막는 설계. 부작용은 "비슷한 닉 못 씀" 정도 |
| 개인정보 유출 | **애초에 수집 안 함.** 이메일·전화·실명 입력칸 자체가 없다. 푸터에 명시: `여기 쓰신 글은 누구나 볼 수 있어요. 개인정보는 적지 말아주세요.` |
| 사장님 초상권 / 명예 | 규칙 3·4·6번으로 1차 방어, 범쨩 삭제로 2차. 푸터 비공식 고지 필수. **사장님이 내려달라 하시면 즉시 내린다** — 이 원칙을 범쨩 패널 상단에 적어둔다 |
| 미성년자 이용 | 연령 확인 수단 없음. 성적 표현 금지를 규칙 1·2에 포함하고 범쨩이 즉시 삭제 |
| 삭제 요청 | 푸터: `내 글 전부 지우고 싶으시면 사우나범 인스타 DM 주세요. 범쨩이 처리합니다.` |
| 페이지 재배포로 URL 변경 | DB는 아티팩트에 묶여 있다. **같은 아티팩트를 업데이트**해야 데이터가 유지된다. 새 아티팩트로 publish 하면 데이터가 전부 날아간다 — 배포 담당자가 반드시 알아야 할 항목 |
